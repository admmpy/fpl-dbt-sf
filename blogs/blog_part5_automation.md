# My FPL Project Part 5: Automation and the Optimization Brain

With the data refinery running smoothly in dbt, the final challenge was connecting everything and giving the system a "brain" to make actual decisions. I used Prefect to manage the flow and cvxpy to solve the team selection puzzle.

### Orchestration: The Master Recipe
I created a new flow called `fpl_weekly_orchestration`. This is like a manager that ensures everything happens in the right order:
1.  **Ingestion:** Pull raw data from the API.
2.  **dbt Build:** Clean and transform that data into features.
3.  **ML Inference:** Predict points for the next week.
4.  **Optimization:** Pick the best squad.
5.  **Notification:** Send the final team to Slack.

**The "Stale Data" Safety Net:** I learned that in the real world, things break. If a dbt test fails on a Tuesday morning, I don't want the whole pipeline to crash. I built logic that says: "If dbt fails, it's okay—just use the data we had from last time so we still get a team recommendation before the deadline."

### MLOps: Normalizing for "Relative Greatness"
In my ML task, I implemented **Z-Score Normalization**. 
*   **The Rationale:** A player scoring 10 points in a high-scoring week isn't as impressive as someone scoring 10 points when the league average is only 3. 
*   **The Fix:** I calculate how many "standard deviations" a player is from the average of that specific week.
*   **Avoiding Selection Bias:** I only include players who actually played (`minutes_played > 0`) when calculating the league average. This ensures bench-warmers don't skew the results.

### Handling the "Cold Start"
I realized that 5-week rolling averages don't work in Gameweeks 1-3 because there isn't enough history. I added code to automatically drop these "noisy" early weeks from training. This ensures the model only learns from high-quality, stable data.

### Optimization: Solving the Puzzle with cvxpy
Instead of a simple "pick the players with most points" script, I used **Mixed-Integer Programming**. I had to code all the complex FPL rules as mathematical constraints:
*   **The Budget:** Exactly £100m total.
*   **The Formation:** 15 players with specific position counts (2-5-5-3).
*   **The Starting XI:** Minimums for each position (e.g., at least 3 defenders).
*   **Team Limit:** No more than 3 players from any single Premier League club.

I even added logic to pick a **Captain** and **Vice-Captain**, where the Captain's points are doubled in the optimization objective.

### The "Last Mile" Debugging
Building this taught me that real-world data is messy. During testing, I hit two major blockers:
1.  **Missing Historical Costs:** Some older records didn't have a price. I had to update my SQL to `COALESCE` the historical cost with the player's current value to keep the optimizer from crashing.
2.  **The Math Solver:** I originally didn't have the right "math engine" installed. I had to learn how to install the `ECOS_BB` solver and its dependencies (`cvxopt`, `ecos`) to handle the "Yes/No" decisions of squad selection.

### Planning for the Long Game
My optimizer doesn't just look at next week. It uses a **5-week rolling horizon**. This prevents the system from "panic buying" a player who has one easy game followed by four hard ones. It maximizes for long-term consistency, which is the key to winning FPL.

Now, the entire pipeline is ready to be scheduled. It is possible to allow the pipeline to run independently with slack notification enabled. Long term, I wish to use cloud scheduler as the drawback of the current approach is that my macbook has to be awake.
